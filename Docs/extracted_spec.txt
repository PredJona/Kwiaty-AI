1. Visión y alcance
Kwiaty será un asistente personal híbrido para uso diario, orientado principalmente a CachyOS y al entorno técnico del usuario. Combinará conversación, control del escritorio, diagnóstico del sistema, ayuda de desarrollo, automatizaciones y memoria local controlada.
Definición del MVPKwiaty v1 será un asistente local-first para CachyOS capaz de conversar, diagnosticar el sistema, usar herramientas controladas, ejecutar acciones según niveles de riesgo, mantener memoria básica y realizar automatizaciones simples desde una ventana flotante o una CLI.
1.1 Objetivos
Reducir fricción en tareas cotidianas del escritorio sin depender permanentemente de Internet.
Permitir diagnóstico real del sistema usando datos y herramientas, no solo respuestas genéricas del LLM.
Mantener el control humano sobre acciones sensibles mediante políticas de riesgo independientes del modelo.
Conservar contexto útil y memoria básica sin almacenar indiscriminadamente conversaciones, capturas o secretos.
Servir como asistente técnico para Linux, Git, Docker y programación sin intentar reemplazar un IDE completo.
Permanecer ligero en reposo y cargar recursos pesados solo cuando la tarea lo requiera.

4. Arquitectura del sistema
La arquitectura elegida es un núcleo modular con herramientas y un adaptador específico de CachyOS. El Core concentra la orquestación y las políticas; las interfaces y proveedores se conectan a él mediante contratos definidos.

5. Flujo del software
Figura 2. Flujo general de procesamiento de una petición.
5.1 Flujo base
1.  La interfaz entrega la petición al Orchestrator.
2.  El Intent Router decide si existe una ruta determinista o si se requiere razonamiento.
3.  El Context Manager reúne solo el contexto necesario.
4.  Si hace falta IA, el Model Router utiliza Ollama por defecto y solo considera cloud según política.
5.  Si el modelo solicita una capacidad, el Tool Manager valida herramienta y parámetros.
6.  El Permission Manager determina si la acción se ejecuta, se confirma, se autentica o se rechaza.
7.  La tool se ejecuta a través del Platform Adapter cuando corresponde.
8.  Kwiaty verifica el resultado de acciones relevantes.
9.  El Orchestrator construye la respuesta final y el Audit Logger registra la actividad.
5.2 Rutas de procesamiento
Ruta
Cuándo se usa
Ejemplo
Rápida
Acciones simples y deterministas; evita cargar LLM innecesariamente.
“Abre Firefox”, “muéstrame RAM”.
Inteligente local
Interpretación, diagnóstico, conversación o planificación mediante Ollama.
“¿Por qué la laptop está lenta?”
Híbrida

“Busca si este error corresponde a un bug reciente”.
5.3 Ciclo de herramientas
Usuario: “Averigua por qué Docker no inicia”↓get_service_status("docker")↓get_service_logs("docker")↓read_file(configuración relevante)↓LLM propone corrección↓Permission Manager → R2↓Usuario confirma↓Aplicar cambio → verificar Docker → responder
El Orchestrator deberá imponer límites de pasos, tiempo, llamadas al modelo y herramientas para impedir ciclos infinitos. Los valores exactos quedan para la fase de implementación.
6. Model Router y Context Manager
6.1 Model Router
Ollama será el proveedor principal en v1.
El resto del Core no conocerá directamente a Qwen; pedirá una operación genérica al Model Router.
Cloud funcionará como fallback opcional y condicionado por políticas de privacidad.
La arquitectura quedará preparada para perfiles FAST/BALANCED/DEEP/VISION, pero v1 solo necesita LOCAL/CLOUD.
El fallo de Ollama no deberá deshabilitar las funciones deterministas del sistema.
6.2 Context Manager
Separa contexto de sesión, memoria relevante, contexto dinámico del sistema y resultados de tools.
No inyecta automáticamente toda la memoria ni todo el historial conversacional.
El estado dinámico (CPU, batería, app activa, red) se consulta cuando hace falta y no se convierte en memoria.
Las capturas de pantalla se usan solo bajo demanda y no se almacenan permanentemente por defecto.
Regla de privacidad cloudAntes de utilizar un proveedor externo, Kwiaty deberá aplicar la política de datos y sanitizar secretos como contraseñas, API keys, tokens, cookies, claves SSH y contenidos sensibles de .env.
7. Sistema de herramientas
Qwen u otro LLM no recibirá una terminal irrestricta. Dispondrá de capacidades declaradas y validables. Cada tool define metadatos que el Core puede comprobar sin confiar en el modelo.
7.1 Contrato mínimo de una herramienta
namedomaindescriptionparameters/schemarisk_levelrequires_networkrequires_privilegesoffline_availablesupported_platforms

Dominio
Responsabilidad

Abrir/cerrar apps, procesos, CPU/RAM/disco/batería, estado y control de servicios.
Diagnostics
Resumen del sistema, errores recientes, logs, procesos de alto consumo, salud del sistema.

7.3 Shell Executor controlado
La flexibilidad de terminal se conserva mediante un executor especial, pero antes de ejecutar un comando deberá separar ejecutable y argumentos, detectar pipes/redirecciones/subshell, identificar privilegios y calcular riesgo. Un comando generado libremente por el modelo nunca se ejecuta sin pasar por esta capa.
ls -lah                 → lectura / bajo riesgosystemctl restart docker → modificación / confirmarsudo pacman -S ...       → acción crítica / autenticaciónrm -rf /                 → RX / rechazar
7.4 Resultados de tools
Las herramientas devuelven hechos, no conclusiones conversacionales. El formato común deberá incluir éxito, datos, error y metadatos. El LLM será responsable de interpretar esos datos y explicarlos al usuario.

8.1 Reglas de seguridad
El riesgo se asigna a herramientas/operaciones y no puede reducirse porque el LLM “considere” segura una acción.
Kwiaty no guarda contraseñas. La autenticación R3 deberá delegarse a mecanismos del sistema como polkit/sudo.
Las automatizaciones no saltan permisos; cada paso conserva su nivel de riesgo.
El sistema debe considerar riesgo acumulativo de secuencias aparentemente inocuas (p. ej. descargar + ejecutar).
Contenido web, archivos y salidas externas se consideran datos no confiables y no pueden redefinir políticas.
Logs de auditoría deben omitir o redactar secretos detectados.
8.2 Política de datos para cloud
Categoría

9. Memoria persistente y contexto
Kwiaty distinguirá memoria persistente de contexto temporal. No almacenará por defecto conversaciones completas ni telemetría continua.
9.1 Categorías de memoria
Categoría
Ejemplos

Largo plazo

Nombre, ruta, stack, herramientas asociadas.
Largo plazo

“mi IDE”, “proyecto de mensajería”, “servidor local”.

9.2 Reglas
La memoria explícita tiene prioridad sobre inferencias automáticas.
En v1, Kwiaty puede sugerir guardar algo, pero no debe almacenar inferencias silenciosamente.
Credenciales, tokens, cookies, claves SSH, .env, logs completos y capturas no se convierten en memoria ordinaria.
El usuario puede crear, consultar, actualizar y eliminar recuerdos.
Recuerdos contradictorios de la misma clave deben actualizarse en lugar de acumularse sin control.
Se recuperan pocos recuerdos relevantes para una tarea en lugar de cargar toda la base.
9.3 Almacenamiento
Para el MVP se recomienda almacenamiento local ligero (por ejemplo SQLite + metadatos y búsqueda tradicional). Una base vectorial/embeddings no forma parte del diseño inicial y solo se añadirá si la escala real de memoria lo justifica.
10. Automation Engine y proactividad
Figura 4. Ejemplo de automatización con permisos y verificación.
10.1 Automatizaciones
Una automatización es una secuencia conocida y reutilizable; una tarea agente es un objetivo abierto gestionado por el Orchestrator.
Las automatizaciones pueden aceptar parámetros, por ejemplo development_environment(project="Wasa").
Cada paso conserva su clasificación R0/R1/R2/R3/RX.
Acciones relevantes se verifican antes de continuar.
El usuario puede cancelar una automatización en el siguiente punto seguro.
Las herramientas que modifican configuración deberán declarar si ofrecen rollback y, cuando sea práctico, crear copia de seguridad.
Crear una nueva automatización en v1 requiere propuesta de pasos + revisión del usuario; no se activa silenciosamente.

11. Interfaz flotante y CLI
11.1 Ventana flotante
Figura 5. Mockup conceptual de la ventana flotante compacta y expandida.
Atajo global propuesto: Super + K.
Estados: COLLAPSED, INPUT, WORKING y EXPANDED.
Las tareas simples pueden responder de forma corta y cerrar la ventana; las complejas expanden la superficie.
Las confirmaciones R2 muestran acción, motivo y riesgo; las R3 añaden consecuencia, reversibilidad y autenticación del sistema.
La UI debe indicar discretamente Local/Cloud y permitir mantener local una petición cuando corresponda.
El progreso muestra operaciones observables (“Leyendo logs…”) y no razonamiento privado del modelo.

15. Fuera de alcance y evolución futura
15.1 Deliberadamente fuera de Kwiaty v1
Sistema multiagente con agentes especializados independientes.
Asistente de voz permanente / wake word y pipeline STT/TTS completo.
IDE completo o editor avanzado de código.
Administrador gráfico completo de archivos.
Observación continua de pantalla.
Plataforma pública de plugins/extensiones.
Integraciones de calendario, correo, Spotify u otros servicios externos.
Recordatorios/notas como módulo principal.
Avatar 3D, HUD futurista u overlays complejos.
Base vectorial/embeddings obligatoria para memoria.
Soporte oficial inicial para Windows, macOS u otras distribuciones.
15.2 Evolución prevista
La arquitectura permite añadir voz, múltiples proveedores/modelos, plugins e incluso agentes especializados en el futuro sin convertir esas posibilidades en dependencias del MVP. La evolución deberá justificarse por necesidades observadas durante uso real.

17. Resumen ejecutivo de arquitectura
Arquitectura aprobadaKwiaty v1 utiliza un Core modular con Orchestrator, Context Manager, Model Router, Permission Manager, Tool Manager, Automation Engine, Memory Manager, Proactive Monitor y Audit Logger. Las capacidades del sistema se exponen mediante tools controladas y un Platform Adapter para CachyOS. Ollama es local-first y cloud es un fallback regulado. La ventana flotante y la CLI comparten el mismo Core.
Usuario  ↓Ventana flotante / CLI  ↓Orchestrator  ├─ Intent Router  ├─ Context + Memory  ├─ Model Router → Ollama / Cloud  └─ Tool Manager       ↓     Permission Manager       ↓     Tools / Automation       ↓     CachyOS Adapter       ↓     Sistema operativo       ↓     Verificación + Audit + Respuesta
La restricción más importante del diseño es deliberada: el LLM nunca es la autoridad de seguridad y nunca obtiene acceso directo e irrestricto al sistema. Esta separación permite cambiar modelos, ampliar herramientas y evolucionar Kwiaty sin entregar el control del equipo al texto generado por un modelo.
Este documento cierra la fase de diseño conceptual consolidado. El siguiente artefacto, cuando se apruebe esta especificación, debería ser un plan de implementación por fases y tareas verificables, manteniendo el alcance del MVP aquí definido.
